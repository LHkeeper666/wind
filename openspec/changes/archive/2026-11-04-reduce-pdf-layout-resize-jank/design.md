## Context

列宽拖动的 `mousemove` 直接更新布局 store。PDF 预览的 ResizeObserver 随之调用页面渲染更新；当前可见区域签名变化会使渲染 generation 失效并重新入队。2026-11-04 10:42 附近日志出现密集瓦片渲染与 ResizeObserver 循环错误。现有 PDF 缓存及单任务优先级队列应继续复用。

## Goals / Non-Goals

**Goals:** 拖动期间保持列宽实时反馈和已有 PDF 画面；限制每帧布局提交；在稳定宽度下尽快补齐可见瓦片；避免过期预取挤占渲染队列。

**Non-Goals:** 改变 PDF 缩放语义、缓存预算、PDFium 并发数或其他预览器的渲染策略。

## Decisions

1. 面板拖动保存最新鼠标位置，并通过单个 `requestAnimationFrame` 提交列宽。松手时提交最后位置并清理待执行帧。相比固定时间节流，这能与屏幕刷新同步且不会丢失最终比例。
2. 将拖动状态传给 PDF 预览。拖动期间仅调整容器和现有瓦片的显示尺寸，延后视口瓦片集合的重新计算；松手或宽度稳定约 150–200 ms 后执行一次更新。窗口本身的尺寸变化也采用相同稳定判定。保留既有画面，避免拖动时空白。
3. ResizeObserver 记录上次实际 `clientWidth`，宽度未变时不触发渲染；同一帧只安排一次更新，并在组件卸载时取消计时与动画帧。观察回调不直接写会改变被观察尺寸的布局。
4. 尺寸变化期间不添加预取任务；稳定后使旧 generation 的待执行任务失效，按既有优先级先渲染当前视口。已开始的 PDFium 请求无法同步中断，其返回结果按 generation 丢弃，不提高并发数。

## Risks / Trade-offs

- 拖动中旧瓦片可能暂时模糊或露出未缓存区域 → 保持已有瓦片并在稳定后优先补齐当前视口低清画面。
- 稳定判定会推迟最终高清画面约 150–200 ms → 松手立即触发更新，仅对仍在连续变化的窗口尺寸使用延时。
- 列宽更新和 PDF 回调可能在卸载后执行 → 统一取消 pending frame、timer 和 observer。

## Migration Plan

无持久化格式变更。实现后运行类型检查与相关测试，再用同一 PDF 对比连续拖动时的帧耗时、渲染请求量和松手后的清晰画面延迟；若回归，可回退前端调度改动。

## Open Questions

稳定窗口的具体时长以手动拖动和性能记录验证，初值采用 150–200 ms。
