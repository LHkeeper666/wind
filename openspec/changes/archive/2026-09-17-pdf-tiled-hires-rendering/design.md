## Context

现有 `PdfPreviewPanel` 已实现连续滚动、页级虚拟化、低清到高清的渐进绘制，以及基于 generation 的单请求队列。它请求 `render_pdf_page(path, page, scale)`，后端用 PDFium 生成固定 `RENDER_SCALE=2` 的整页 JPEG；前端将 Canvas 的 CSS 尺寸设为 `pagePoints * zoom`。因此放大不会提高实际像素密度，最大 500% 缩放会把同一整页位图继续插值放大。

应用运行在 Windows Tauri/WebView2 中，后端已经使用 PDFium 和文档 LRU 缓存。PDF 预览还承担搜索高亮、链接覆盖层、书签跳转和连续滚动定位，方案必须保留这些行为。PDFium 调用目前由全局 Mutex 串行化；在高倍率下先生成完整页面再裁剪会导致位图分配、JPEG 编码和 IPC 传输都与整页面积成正比。

## Goals / Non-Goals

**Goals:**

- 缩放停止后，让可见 PDF 内容以匹配逻辑缩放和 `devicePixelRatio` 的栅格密度显示，避免 CSS 放大旧图造成的明显模糊。
- 在滚动、缩放和高速跳页时优先保障当前视口，并将已失效任务的结果排除在显示和缓存之外。
- 将高倍率渲染的峰值内存和 IPC 数据量限制为可见区域附近的瓦片，而不是整个页面。
- 复用现有连续滚动、页尺寸占位、导航、搜索和 PDFium 文档缓存。

**Non-Goals:**

- 不替换 PDFium 为 PDF.js，不引入浏览器内嵌 PDF 查看器。
- 不实现文本选择层、批注编辑、旋转页面或全屏查看器的架构迁移。
- 不保证 PDF 中可填写表单在瓦片模式下可编辑；现有仅预览模式保持为目标。
- 不对 PDF 文件、数据库结构或用户配置进行迁移。

## Decisions

### 1. 采用直接渲染的页内瓦片，而非提高固定整页分辨率

一个逻辑页面继续以 PDF point × `zoom` 作为 CSS 尺寸。每一块瓦片固定为 `512 × 512` 物理像素（边缘块可更小），其页面坐标、逻辑 CSS 坐标和物理位图坐标由统一的 `renderScale = zoomBucket × max(2, min(devicePixelRatio, 2))` 转换，以保留原预览的 2× 基础超采样清晰度。

后端新增 `render_pdf_tile`，输入文件、页码、量化缩放档位、瓦片左上物理坐标和瓦片物理尺寸，输出编码图像及实际尺寸。实现直接调用 PDFium 的位图渲染接口：目标 bitmap 仅分配瓦片大小，而整页映射使用 `start_x/start_y` 负偏移或等价变换。不得使用 `PdfRenderConfig::clip()` 作为瓦片实现，因为该封装仍按完整输出尺寸分配 bitmap，且会禁用表单数据绘制。

选择 512 px 而不是 256 px：前者显著减少 Tauri IPC、JPEG/图像解码和 DOM 节点数；与一屏可见区域相比仍能精确控制高倍缩放的内存。设备较慢时可通过后续性能数据评估 384 px，不在第一版引入自适应尺寸。

备选方案是按 `zoom × DPR` 重绘可见整页。它适合作为原型，但 A4 页面在 500% 和 DPR 2 下约为 5950 × 8420 像素，仅一张 RGBA 位图约 191 MiB，不能作为最终方案。保持固定高分辨率整页或仅提高 `RENDER_SCALE` 同样无法满足高倍率场景。

### 2. 缩放采用两阶段显示与量化档位

每次缩放输入先立即更新布局和既有图层的 CSS 变换，保持视口锚点不变；这一步允许短暂的旧图模糊。最后一次 Ctrl+滚轮或快捷键缩放后等待 150 ms，计算当前 `zoom` 对应的 `zoomBucket`，再请求可见瓦片。缩放档位按 1/8 逻辑比例量化，并限制在现有 30%~500% 范围内；同一档位内的小变化复用瓦片。

新瓦片到达后按 tile 替换旧图，不等待整页完成。渲染比例包含最高 2 倍设备像素比，兼顾高 DPI 清晰度和预算；超过 2 的 DPR 使用 2 作为上限。每块瓦片在 CSS 中以精确的逻辑尺寸定位，尺寸和位置采用整数物理像素转换，避免相邻块因小数舍入出现缝隙。

备选方案是每个缩放事件立即渲染高分辨率内容。它会在滚轮连续输入期间创建大量马上过期的 PDFium 任务，反而降低交互响应，因此采用延迟稳定后的升级。

### 3. 视口瓦片集合、调度和取消继续使用 generation 模型

前端以滚动容器的可见矩形与每页 slot 的交集计算所需瓦片，而不是只按页号确定渲染范围。当前视口的瓦片为最高优先级；滚动方向前方一行/列瓦片为次级预取；其余相邻页和旧的低清占位为最低优先级。仍同时最多执行一个 PDFium 渲染请求，以匹配现有文档 Mutex 和避免编码争用。

每次缩放档位、PDF 路径或可见 tile 集合发生实质变化均递增 generation。队列中尚未开始的旧任务必须被拒绝；已开始任务可以完成，但前端只有在 tile key 和 generation 均匹配时才绘制和缓存。瓦片到达顺序不影响最终显示。

为避免空白，首版保留现有低分辨率整页作为临时占位，仅覆盖当前可见页面；高清瓦片开始可用后淘汰同区域的低清 Canvas。页面离开页级缓冲范围后移除 DOM 瓦片，但可保留可复用缓存条目。

### 4. 使用以解码像素为准的双层 LRU 缓存

瓦片键为 `{pathRevision, page, zoomBucket, dprBucket, tileX, tileY}`。路径切换、文件修改时间变化和缩放 generation 都不会错误复用旧键。缓存成本按 `tileWidth × tileHeight × 4` 计算，而不是按 base64 或 JPEG 压缩后字节数估算，因为 WebView 的 Canvas/图像解码占用由像素数决定。

高清和低清瓦片共用既有 96 MiB 总预算，临时低清占位子预算为 16 MiB。当前视口及一个预取环固定（pinned）；达到预算时按 LRU 先淘汰低清、非当前缩放档位和不可见瓦片。DOM 元素由页级缓冲控制，缓存数据由预算控制，两者独立但均受同一可见集合约束。

既有页面缓存不能与瓦片缓存共享 key 或容量统计；实施时以统一缓存接口替换它，确保不会同时保留同一页的多份整页高清图和瓦片图。

### 5. 维持页面语义和覆盖层坐标体系

页面 slot 尺寸、滚动偏移、书签跳转及链接覆盖层继续使用 PDF point × 逻辑 zoom，不依赖瓦片像素密度。搜索结果也保留 PDF point 坐标：高亮绘制到相交瓦片时先把结果矩形裁剪、再转换为 tile 内物理坐标。链接覆盖层仍位于整页 wrapper 的逻辑坐标系，不按瓦片拆分，避免点击区域出现边界误差。

首版瓦片图像沿用 JPEG 传输但将文本可读性作为验收指标；若测试确认压缩伪影在常见文本 PDF 中可见，改用 PNG 或 WebP。由于 Tauri JSON 返回 base64 会额外复制数据，后续若 IPC 成为主瓶颈，可单独变更为自定义协议流式传输，不与本变更绑定。

## Risks / Trade-offs

- [PDFium 瓦片坐标映射产生偏移、翻转或页面边缘接缝] → 用带网格、文字和不同页面尺寸的固定 PDF 建立坐标测试；瓦片向右/下多渲染 1 个物理像素并以 CSS 裁剪。
- [高频滚动使串行 PDFium 队列落后于视口] → generation 取消、中心优先、方向预取以及 150 ms 缩放防抖；记录队列等待和首块到达时间。
- [缓存低估浏览器内存或当前瓦片无法淘汰] → 按解码 RGBA 字节记账，限制 pinned 集合为视口加一圈，并在路径/缩放档位切换时主动驱逐旧条目。
- [JPEG 压缩抵消分辨率提升] → 对文字、扫描件和照片 PDF 分别进行视觉验证；必要时选择无损或更高质量编码。
- [带交互表单的 PDF 在矩阵/偏移绘制下与原整页渲染不一致] → 首版将其视为只读预览限制，并在测试样本中验证普通注释与链接仍正常。
- [搜索高亮和链接覆盖层与瓦片错位] → 保持 PDF point 为唯一语义坐标，单独覆盖缩放、横向滚动和跨页场景。

## Migration Plan

1. 先在现有 PDF 面板中增加瓦片坐标、渲染命令和缓存单元测试，不改变默认展示路径。
2. 以低清整页占位 + 高清瓦片替换可见页的固定整页高清渲染，并保留现有 generation 与页级虚拟化。
3. 使用代表性 PDF 验证 100%、200%、500% 与 DPR 1/2 的清晰度、内存和导航行为，再移除不再使用的整页高清预加载代码。
4. 若发布后发生白页、接缝、性能退化或链接/搜索错位，回退到现有整页渲染路径；后端新命令和缓存键均为新增，不影响文件数据。

## Open Questions

- JPEG 95 是否已足以满足矢量文字清晰度，还是应在首版直接使用 PNG/WebP？应由本机样本和包体/延迟测量决定。
- 512 px 是否在目标设备上优于 384 px？首版先固定 512 px，并通过指标决定是否需要设备自适应。
- 全屏 PDF 查看器是否应后续复用瓦片引擎？本变更不改动它，但共享工具层的抽取应避免阻断后续复用。
