## Context

`PdfPreviewPanel` 以连续滚动和页面占位实现虚拟化。页面槽会居中放置固定宽度的页面包装器，但页面槽自身裁剪溢出，导致滚动容器的 `scrollWidth` 不会随放大后的页面增加。组件已处理 `h/l`，却没有可移动的水平范围。

前端分别使用低清和高清 `PdfPageCache`，缓存仅按页码索引且没有淘汰策略；页面滚出可视缓冲区时仅销毁 canvas。预加载会同时提交多项请求，而后端在 Pdfium 渲染阶段由全局 mutex 串行化，随后 JPEG 编码和 Base64 转换可重叠，容易在快速滚动时累积过期工作和临时内存。后端还按路径保存已打开的 Pdfium 文档，必须为其提供受限的、真实释放 native 文档资源的生命周期。

## Goals / Non-Goals

**Goals:**
- 让超出 PDF 视口宽度的页面产生原生横向滚动范围，并使 `h/l` 平移该范围。
- 让 PDF 目录可从预览通过 `Ctrl+W l` 聚焦，并通过 `Ctrl+W h` 返回预览；书签跳转保留目标页内 y 坐标。
- 对栅格页数据、渲染请求和后端文档缓存设置可预测的容量和生命周期边界。
- 始终优先完成当前可见页，避免后台预加载阻塞交互。

**Non-Goals:**
- 不实现基于缩放和 DPR 的高清重渲染、瓦片渲染或文字选择层。
- 不改变 PDF 搜索、链接跳转、全屏单页查看器或目录树已有的 `j/k/h/l/Enter` 语义。
- 不修改 PDF 文件、书签或表单内容。

## Decisions

### 1. 以页面轨道提供横向溢出

在滚动容器中新增页面轨道，其宽度为 `max(viewportWidth, widestPageWidth * scale)`。每个页面槽占满轨道宽度，页面包装器在轨道内居中；槽不再裁剪横向内容。这样保留页面居中显示，同时让浏览器计算正确的 `scrollWidth`。`h/l` 仅在存在横向可滚动距离时改变 `scrollLeft`，并消费按键。

替代方案是在每个页面槽上保留 `overflow: hidden` 并用 CSS transform 平移页面。该方案不能使用原生横向滚动条、无法和鼠标或触控板保持一致，也会使链接覆盖层坐标更复杂，故不采用。

### 2. 使用显式目录焦点协议

`PanelLayout` 在 PDF 预览收到 `Ctrl+W l` 时聚焦 `PdfTocSidebar`，目录收到 `Ctrl+W h` 时归还焦点给 PDF 预览。目录收到非搜索状态的 `Escape` 时也通过回调归还焦点；`Escape` 在目录搜索状态中仍先关闭搜索。目录跳转回调传递页码和 y 坐标，并调用现有坐标换算路径滚动到书签目标。

替代方案是让目录保持 DOM 焦点并由父组件推断焦点状态。该方案会让全局快捷键和目录组件的键盘处理竞争，故采用显式回调。

### 3. 前端采用按字节计量的分级 LRU 栅格缓存

将低清和高清图像统一为带变体键的缓存，键包含文档标识、页码和渲染变体。缓存记录 Base64 字节数、最近访问时间与优先级。默认压缩图总预算为 `96 MiB`，其中低清预览最多占 `16 MiB`；超出预算时优先淘汰低清条目，再淘汰未固定的最久未使用高清条目。当前可见页和正在显示的相邻页固定，高清条目写入成功后删除同页低清条目。

DOM canvas 不放入该缓存；继续由虚拟化窗口控制。缓存预算以传输/保留的图像字节为准，而不是 JPEG 解码后的瞬时像素内存。

替代方案是固定“最多 N 页”。页面大小和 JPEG 压缩率差异极大，页数限制无法约束内存，故不采用。

### 4. 使用单消费者优先级渲染队列

前端维护一个全局于当前 PDF 面板的队列，最多同时派发一个 `render_pdf_page` 请求。任务优先级为：可见页高清、可见页低清、相邻页高清、相邻页低清、后台低清预加载。视口或文档切换递增 generation，执行前和结果返回后均校验 generation；失效请求的结果不绘制、不进入缓存。

单请求并发与后端 Pdfium mutex 的串行特性一致，避免多个请求已拿到 RGBA 图后并发编码造成峰值内存。可见任务进入队列时可以移除尚未开始的低优先级任务。

替代方案是保留 `Promise.all()` 预加载并仅依赖 mutex。mutex 不限制锁外的 JPEG/Base64 工作，也无法表达可见页的抢占优先级，故不采用。

### 5. 后端文档缓存容量与释放

后端文档缓存限制为最近使用的 4 个路径。淘汰、主动清理和应用退出时必须调用 Pdfium 的 native 文档关闭 API，而不是只清空 `HashMap`；同时保证没有正在执行的命令持有被关闭的文档。Pdfium 实例仍可保持进程级生命周期。

替代方案是只在前端切换文件时调用现有 `clear_pdf_cache`。现有命令只清空容器，而 `PdfDocument` 没有 Drop 释放 native handle，不能满足内存回收目标，故不采用。

## Risks / Trade-offs

- [单请求队列降低远端预取吞吐] → 本地 Pdfium 已串行渲染；以可见页延迟和稳定内存优先，后续可在度量后增加低优先级预取并发。
- [96 MiB 缓存预算在高分辨率显示器上命中率较低] → 预算与低清子预算集中定义，后续可按性能数据调整而不改变行为协议。
- [关闭 native 文档可能与正在渲染的借用冲突] → 所有文档访问继续在同一 mutex 内完成；仅在无活跃借用时淘汰，并为打开/切换/清理路径添加测试。
- [页面轨道宽度随缩放变化] → 缩放后保留视口中心的逻辑不变，轨道宽度与页面高度在同一次 DOM 更新中同步计算。

## Migration Plan

该变更不涉及持久化数据或外部 API 兼容性。先落地前端轨道、焦点协议和缓存/队列单元测试，再替换后端文档缓存释放逻辑。若出现 PDF 渲染回归，可回退至上一版本；缓存数据只存在内存，退出应用即可清除。

## Open Questions

无阻塞问题。`96 MiB` 总预算、`16 MiB` 低清预算和 4 个后端文档的容量作为首版默认值，并在实现中集中为常量。
