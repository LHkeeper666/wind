## Context

`PreviewEditor` 当前只有一个条件挂载的 `PdfPreviewPanel`。切 tab 会销毁它，触发瓦片缓存、canvas 和全局 PDF 文档缓存清理；恢复的 tab 快照只含页码、缩放与滚动位置。`PdfRenderScheduler` 串行工作，当前排序让可见高清块先于低清块，并按中心距离逐块插入。普通预览已有 per-tab slot，但 PDF 面板不在其中。

## Goals / Non-Goals

**Goals:** 已打开且未失效的 PDF tab 切回时保留可见画面；首次加载或缓存失效时先呈现完整可见区域的低清画面，再提升清晰度；内存与后台渲染有界。

**Non-Goals:** PDFium 并行渲染、改变 PDF 文件格式或全屏阅读器、保证首次打开时零等待。

## Decisions

1. **按 tab 保留 PDF 面板会话。** 在稳定的宿主中按 tab ID 挂载面板，切换时隐藏非活动会话并暂停其新请求，保留 DOM、滚动位置、瓦片缓存和缩放状态。活动会话切换前保存 UI 状态，切回后先显示已绘制画面，再重新检查视口。隐藏方式须保持可测量尺寸，避免 `display:none` 导致缩放重算。相比将 canvas 序列化成截图，这保留清晰瓦片与交互层，也避免复制像素。普通非 PDF tab 继续走原有预览 slot。
2. **限制保留成本。** 活动会话沿用现有 96 MiB 瓦片预算；为所有非活动 PDF 会话设置 96 MiB 合计预算与三个会话的数量上限，并按最近使用顺序释放最旧会话。被释放的会话仍保存 tab 的页码、缩放和滚动快照，回访走低清首屏路径。关闭 tab、改变其文件、检测到文件 mtime 改变时立即释放对应会话。后端的全局 `clear_pdf_cache` 不再由任意面板卸载触发；新增按路径失效命令处理文件变化，其他文档仍由现有 LRU 管理。
3. **低清首屏作为一组提交。** 对初次或失效视口先排可见低清瓦片，待全部解码并绘制到隐藏层后在同一帧显示该层；设置 500 ms 上限，超时后允许已完成部分显示，以免单块失败造成长时间空白。可见高清任务随后执行，并逐块覆盖低清。缓存命中时立即显示，无需等待批次。滚动或缩放后旧画面在新画面准备期间保留可用区域，generation 防止旧结果进入新视口。
4. **调度分阶段。** 队列仍最多派发一个 PDFium 请求。首屏低清可见请求优先于高清可见请求，所有可见请求优先于预取；完成低清提交后恢复高清优先。非活动会话暂停预取与新渲染。这样减少拼图感而不引入后端并发锁争用。

## Risks / Trade-offs

- **保留多个 DOM/canvas 增加内存** → 非活动会话合计预算和 LRU 释放；测试多 tab 与大 PDF。
- **低清等待最慢瓦片延迟首帧** → 短超时与失败降级；记录首帧和完整视口时间。
- **文件已改变但旧画面瞬时显示** → 已知 mtime/文件监听事件先失效；回访时异步校验并在发现变化后清理重载。
- **隐藏面板的尺寸或焦点异常** → 保持布局尺寸，激活时复核 ResizeObserver 和焦点目标。

## Migration Plan

先引入按 tab 的 PDF 宿主与释放策略，再加入低清批量提交和队列阶段。无需持久数据迁移；回退时恢复单面板挂载方式。

## Open Questions

非活动会话的合计预算与低清批次超时已采用保守初值，仍需用真实 PDF 性能数据验证并调整。
